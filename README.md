# GravityGame — Mobile Prototype

Open `Assets/Scenes/MobilePrototype.unity` and press Play. The separate mobile scene preserves TwoPlanets and PhaseOne. Use landscape orientation; mobile runtime supports both landscape directions and targets 60 FPS (device performance still needs measurement).

An Android test APK of the earlier joystick prototype is available locally at `Builds/MobilePrototype/GravityGame-Prototype.apk` (Android 8.0+, ARM64, about 43 MB). Its development build and APK signature were verified; rebuild it to include the new landing-victory feature. Generated artifacts are ignored by Git; physical-phone testing is still outstanding.

- **Left joystick:** partial movement walks, pushing near the edge runs automatically. A dead zone prevents small accidental movement; a separate run button is unnecessary.
- **Jump:** tap the large right button. It turns gold and reads **HIGH JUMP** once a real run-up is ready. The jump triggers on touch-down; holding it does not repeat jumps. Movement, jump, and look can use independent fingers.
- **Look:** drag the free right-side area. Assistance follows forward movement and frames a planet ahead during flight, without changing gravity or takeoff momentum. A manual drag temporarily overrides assistance.
- **Pause / Resume:** large touch buttons freeze motion and the loss countdown. Focus loss or app interruption pauses and requires an explicit resume. Held touches are cleared to prevent stuck movement or camera motion.
- **Lost in space / Try again:** missing all gravity fields still causes defeat. The retry button returns to the last safe landing; there is no automatic rescue.
- **Victory / Play again:** stay grounded on Ember for a quarter of a second to complete the level. Entering its gravity field or briefly touching the surface is not enough. The character stops, touch controls give way to a **Planet reached!** screen, and **Play Again** starts a fresh attempt on Azure. In the editor, R also restarts after victory. Desktop free-play scenes have no victory target.

Keyboard WASD/arrows, Shift and Space remain for development. Escape toggles pause; the mouse can drag the joystick and look area. R retries while playing or defeated; paused retries use the menu. The mobile scene keeps the pointer unlocked. Desktop scenes retain their original mouse control.

The UI uses a scaling Canvas, safe-area insets, large mesh-drawn circular controls, and text that does not intercept touch raycasts. `MobileTouchControl` tracks each initiating pointer independently; `MobileGameUI` owns UI state and restores the clock when it leaves the scene. No new packages are needed. Use **GravityGame > Create Mobile Prototype** to recreate the scene (it asks to save open edits first). For your own phone build, enable MobilePrototype in your Android/iOS Build Profile; the existing build scene list is preserved.

Validation: run Unity against a temporary or closed project with `-batchmode -nographics -projectPath <project> -executeMethod GravityGame.Editor.MobileDemo.ValidateAll -quit -logFile <log>`. This includes all desktop physics checks, then validates joystick walk/run thresholds, independent pointers, jump/look input, authored UI order, pause/resume, interruptions, safe-area anchors, loss/retry and global clock cleanup. For actual rendered UI raycasts and saved-scene reloading, run `-batchmode -projectPath <project> -executeMethod GravityGame.Editor.MobilePlayModeChecks.Run -logFile <log>` without `-quit`; this run exits itself. It explicitly renders the Canvas because batch editors do not draw a Game view by default. It also captures gameplay, pause, and loss previews in Logs. Actual multi-touch feel, text readability, Android/iOS lifecycle behavior, performance, and heat/battery use must be checked on real devices before release.

The optional `MobileDemo.BuildAndroid` batch entry point requires `-buildTarget Android` and an installed Android toolchain. Run it on a temporary copy: it configures that copy for a development ARM64/OpenGL ES 3 APK (`com.gravitygame.prototype`, target SDK 36) and writes `Builds/GravityGame-Prototype.apk`. The unused experimental `com.unity.pipeline` 0.9.0-exp.1 editor/live-reload package has been removed from the project because its preprocessor queries a desktop-only subtarget on Android. URP, the graphics rendering package, remains installed. Let Unity finish resolving packages before rebuilding; editing Library/PackageCache is unnecessary. This is not a store release. For iOS, build on macOS and enable both landscape orientations in Player Settings; no iOS build or physical-device test has been performed here.

See `ANDROID_READINESS_AUDIT.md` for the Android build and store-readiness review. Run `Tools/Verify-AndroidApk.ps1` after an APK build to check its application identifier, target API, ARM64 support, signature, ZIP alignment and each native library's 16 KB ELF alignment. Add `-RequireRelease` to reject debuggable APKs; this does not replace release signing, an AAB, Play Console review or device testing.

## Desktop prototypes
### Two Planet Demo

Unity **6000.5.9f1**, Universal Render Pipeline, Input System.

Open `Assets/Scenes/TwoPlanets.unity` and press Play. You start on blue Azure, facing orange Ember. **Hold Shift + W** to run toward Ember, then press **Space** after a short run-up (about one second). A running jump can clear Azure's gravity boundary; keep your takeoff momentum through space to enter Ember's field and land. **E no longer launches or switches planets.** WASD/arrows move, either Shift key runs, Space jumps, and the mouse orbits. **R** respawns at your last safe landing. Escape releases the pointer; click to capture it again.

Thin rings mark each planet's gravity boundary, six units above its surface. Gravity fades over the outer 1.5 units and is zero outside. The fields are separated by a gap of space. A normal jump stays inside the field; a running jump needs both Shift and actual movement speed built up on the ground. Running preserves takeoff speed, while releasing movement in the air adds no motor braking. In space, neither gravity nor movement input changes your velocity. Entering another field applies its radial pull automatically; player orientation and the camera turn smoothly to follow. Overlapping fields in custom scenes retain a three-unit switching margin.

Leaving every field starts a three-second countdown. Reach another field in time to continue; otherwise the player loses and a **Lost in space** screen appears. Drifting more than 120 units beyond the nearest surface also loses immediately. There is no automatic return to a planet: the player freezes in space, movement stops, and the mouse is released. Press **R** or click **Retry from last landing** to try again. Safe landings update the retry checkpoint; an explicit retry clears momentum and resets the camera immediately. The loss screen appears even with the normal help panel disabled. Camera obstruction checks include both planets.

Use **GravityGame > Create Two Planet Demo** to recreate the scene. Materials live in `Assets/Materials/TwoPlanets*.mat`. The original PhaseOne and SampleScene files and build scene list are preserved; add TwoPlanets to your build profile to build this demo.

Validation: run Unity on a closed or temporary copy with `-batchmode -nographics -projectPath <project> -executeMethod GravityGame.Editor.TwoPlanetDemo.ValidateAll -quit -logFile <log>`. It checks the original single-planet demo, then uses a temporary Input System keyboard to test both Shift keys, walking/running speed, normal and running jumps, an unassisted crossing, zero-gravity momentum, field entry, landing, the grace countdown, persistent timeout/distance defeat with no automatic teleport, blocked movement after defeat, explicit R/button recovery, and camera clearance/reset. Look for both `PHASE_ONE_VALIDATION_PASSED` and `TWO_PLANET_VALIDATION_PASSED`.

Play mode checklist: compare walking and running with either Shift key; jump without a run-up and confirm you fall back; run toward Ember and jump past the rings, then release movement to coast. Check the countdown stops when Ember captures you. Jump away from both planets and confirm the loss screen appears after the countdown, the character stays in space, and movement cannot resume until R or the Retry button is used. Verify each retry returns to the latest safe landing, and the button remains clickable without the mouse recapturing. Keyboard/mouse feel and rendered camera transitions still require hands-on review.

## Original Phase 1 demo

`Assets/Scenes/PhaseOne.unity` remains available for the original single-planet movement demo.

`PlanetGravity` supplies constant radial acceleration about its transform. `SphericalPlayer` applies gravity in physics steps, aligns a Rigidbody capsule to local up, accelerates along the tangent plane, and probes the assigned planet for grounded jumping. Diagonal input is normalized and airborne steering is reduced. `PlanetCamera` transports its heading with local up, smooths its following position, limits pitch, and prevents the camera from crossing the planet surface.

Assign the starting planet and movement camera in the player Inspector; populate `gravitySources` for multiple planets. Each source uses a centered SphereCollider with uniform scale; the player uses a unit-scale Y-axis capsule. Tune gravity acceleration, influence height, edge falloff, walk/run speeds, normal/running jump heights, air control, gravity turn speed, respawn limits, camera distance, and smoothing in the Inspector. Planets are static in this demo. Empty source lists retain single-planet behavior.

Use **GravityGame > Create Phase 1 Demo** to recreate the demo scene. This prompts to save open scene changes. The original SampleScene and build scene list are preserved; add PhaseOne to a build profile when building the demo.

Manual checks: walk a complete circuit through both poles and the underside; release movement to stop; compare diagonal and straight speed; jump, land, and hold Space to confirm no automatic repeated jump; orbit near the horizon; release and recapture the pointer. Confirm the camera stays outside the planet and the Console has no errors.

Automated validation: with the project closed in the editor, run Unity with `-batchmode -nographics -projectPath <project> -executeMethod GravityGame.Editor.PhaseOneDemo.Validate -quit -logFile <log>`. It recreates PhaseOne, checks scene references and gravity at all six cardinal directions, tests surface probes and the center fallback, and simulates six player drops to confirm grounding. Look for `PHASE_ONE_VALIDATION_PASSED`. Run this on a temporary copy if the project is already open. These checks do not replace the manual input and camera checks above.
