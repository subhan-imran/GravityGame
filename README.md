# GravityGame — Mobile Prototype

## Oxygen survival

The HUD now shows an oxygen bar and percentage instead of seconds remaining in space. It stays full inside any planet's gravity, drains only outside every field, and refills immediately when a field captures the player. The fill changes from cyan to amber/red at low supply, with an explicit **OXYGEN LOW** label. An empty tank opens **Out of oxygen**; it never returns the player automatically. Pause and app-interruption pause freeze oxygen use. Retry refills the tank and keeps collected stars; Play Again refills it and resets the star objective.

`SphericalPlayer.oxygenCapacity` is the tank capacity in seconds (default 3, preserving the previous travel balance). It replaces the serialized `lostInSpaceDelay` with migration support for existing scenes. Increasing the capacity supports longer flights; there is no separate timeout or distance-based death that overrides the tank. Desktop help also shows an oxygen bar. Both authored mobile scenes include the HUD; the existing APK described below predates this update.

Run `GravityGame.Editor.MobilePlayModeChecks.RunOxygen` in a graphics-enabled batch Unity process on a temporary project copy, without `-quit`. It upgrades the saved mobile scenes in place, then checks the authored First Expedition level. Oxygen checks cover drain, bar width, low warning, refill, pause, empty-tank defeat, retry/star persistence, replay and double-capacity survival past the old time and distance limits. Existing route, jump, tutorial, touch and victory checks also run.

Verified October 22, 2026 in Unity 6000.5.9f1: `Logs/oxygen-validation.log` exited 0 with `OXYGEN_VALIDATION_PASSED` and all existing physics, route, star, tutorial and rendered mobile checks passed. Full/low oxygen and defeat screenshots were visually reviewed. Both saved mobile scenes were upgraded without removing or replacing existing scene object identities. Phone behavior still needs the deferred device checklist.

## Two-planet mobile prototype

Open `Assets/Scenes/MobilePrototype.unity` and press Play. The separate mobile scene preserves TwoPlanets and PhaseOne. The game is locked to horizontal Landscape Left at launch, before the splash screen, during gameplay and when returning from the background. Automatic portrait rotation is disabled. Mobile runtime targets 60 FPS (device performance still needs measurement).

The updated Android test APK is `C:/Users/Artemis/OneDrive/Apps/game.apk` (Android 8.0+, ARM64, about 62 MB), built directly to Unity's saved destination on October 22, 2026. The tutorial update adds guided practice, jump/landing/star feedback and strict gravity containment for jumps 1 and 2. The build and fixed-landscape, signature and 16 KB native/ZIP alignment checks passed. Earlier star-exploration APKs remain in `Builds/MobilePrototype`. Generated builds are ignored by Git. See `TUTORIAL_FEEDBACK_PR.md` for validation and the latest build result.

- **Left joystick:** partial movement walks, pushing near the edge runs automatically. A dead zone prevents small accidental movement; a separate run button is unnecessary.
- **Jump:** tap once, land, then tap again within **1.2 seconds** to continue the chain. Jumps 1 and 2 get higher; **jump 3** can escape gravity. The button displays the next stage and turns gold for **ESCAPE 3 / 3**. Running still works for faster movement but cannot skip the chain. Airborne taps do not advance it; holding the button does not repeat jumps. Pausing freezes the landing window; waiting too long, changing planets or retrying resets the chain. Aim your movement toward the next planet for the third jump; jumping straight into empty space can still lose.

- **Tutorial:** a small, nonblocking card teaches movement, jump 1, jump 2, the escape jump and travel through actual play. Tap **SKIP** to explore immediately; **Pause > Replay Tutorial** brings it back without resetting stars or the checkpoint. Completion/skip is remembered on the phone, while editor validation never writes that preference.
- **Feedback:** each takeoff has a distinct soft chime and a short jump message. A landing pulse marks when to tap again; landing after jump 2 highlights the escape jump in gold. Gold sparkles and a chime confirm star pickups. Pause freezes the visual timing and stops current sounds; retry clears stale effects.
- **Look:** drag the free right-side area. Assistance follows forward movement and frames a planet ahead during flight, without changing gravity or takeoff momentum. A manual drag temporarily overrides assistance.
- **Pause / Resume:** large touch buttons freeze motion and oxygen use. Focus loss or app interruption pauses and requires an explicit resume. Held touches are cleared to prevent stuck movement or camera motion.
- **Out of oxygen / Try again:** staying outside all gravity fields until the tank empties causes defeat. The retry button returns to the last safe landing with full oxygen and keeps collected stars; there is no automatic rescue.
- **Stars / Victory / Play again:** explore either planet and collect all **three gold stars** in any order: two on Azure, one on Ember. The counter tracks progress. There is no landing zone or automatic win for reaching Ember. Only the final pickup opens **All stars collected!**. **Play Again** restores all stars and starts on Azure; R also starts a fresh run after victory. Progress survives checkpoint retries within the current session, but is not saved after closing the game. Desktop free-play scenes have no star objective.


Keyboard WASD/arrows, Shift and Space remain for development. Escape toggles pause; the mouse can drag the joystick and look area. R retries while playing or defeated; paused retries use the menu. The mobile scene keeps the pointer unlocked. Desktop scenes retain their original mouse control.

The UI uses a scaling Canvas, safe-area insets, large mesh-drawn circular controls, and text that does not intercept touch raycasts. `MobileTouchControl` tracks each initiating pointer independently; `MobileGameUI` owns UI state and restores the clock when it leaves the scene. No new packages are needed. Use **GravityGame > Create Mobile Prototype** to recreate the scene (it asks to save open edits first). For your own phone build, enable MobilePrototype in your Android/iOS Build Profile; the existing build scene list is preserved.

## Desktop prototypes
### Two Planet Demo

Unity **6000.5.9f1**, Universal Render Pipeline, Input System.

Open `Assets/Scenes/TwoPlanets.unity` and press Play. You start on blue Azure, facing orange Ember. Chain three jumps with **Space**: land and jump again within 1.2 seconds. Jumps 1 and 2 stay in gravity; jump 3 can escape. Walk toward Ember before the third takeoff, then release input to coast into its field. Hold either **Shift** key to run for faster exploration; running alone never unlocks escape height. WASD/arrows move, and the mouse orbits. **R** retries at your last safe landing. Escape releases the pointer; click to capture it again. E has no travel action.


Thin rings mark each planet's gravity boundary, six units above its surface. Gravity fades over the outer 1.5 units and is zero outside. The fields are separated by a gap of space. The first two jumps stay inside the field. The third consecutive grounded takeoff supplies escape height independent of running speed. The first two arcs include inward assistance for surface travel and a spherical height limit inside the full-strength gravity region. The limit checks the next physics position, including movement and gravity, so held running, a larger timestep or extra outward momentum cannot unlock early escape. Jump 3 releases that constraint. Releasing movement in the air adds no motor braking. In space, neither gravity nor movement input changes your velocity. Entering another field applies its radial pull automatically; player orientation and the camera turn smoothly to follow. Overlapping fields in custom scenes retain a three-unit switching margin.

Leaving every field drains the oxygen tank, which holds three seconds by default. Reach another field to refill it; an empty tank opens **Out of oxygen**. Capacity can be increased for longer trips without a separate distance limit ending the flight. There is no automatic return to a planet: the player freezes in space, movement stops, and the mouse is released. Press **R** or click **Retry from last landing** to try again. Safe landings update the retry checkpoint; an explicit retry refills oxygen, clears momentum and resets the camera immediately. The loss screen appears even with the normal help panel disabled. Camera obstruction checks include both planets.

Use **GravityGame > Create Two Planet Demo** to recreate the scene. Materials live in `Assets/Materials/TwoPlanets*.mat`. The original PhaseOne and SampleScene files and build scene list are preserved; add TwoPlanets to your build profile to build this demo.

Validation: run Unity on a closed or temporary copy with `-batchmode -nographics -projectPath <project> -executeMethod GravityGame.Editor.TwoPlanetDemo.ValidateAll -quit -logFile <log>`. It checks the original single-planet demo, then uses a temporary Input System keyboard to test both Shift keys, walking/running speed, increasing chained jumps, an unassisted third-jump crossing without Shift, zero-gravity momentum, field entry, landing, oxygen depletion with no automatic teleport or distance-based death, blocked movement after defeat, explicit R/button recovery, and camera clearance/reset. Look for both `PHASE_ONE_VALIDATION_PASSED` and `TWO_PLANET_VALIDATION_PASSED`.

Play mode checklist: compare walking and running with either Shift key; jump once and confirm you fall back; chain a second and third jump toward Ember and pass the rings, then release movement to coast. Check oxygen refills when Ember captures you. Jump away from both planets and confirm the loss screen appears after oxygen empties, the character stays in space, and movement cannot resume until R or the Retry button is used. Verify each retry returns to the latest safe landing with full oxygen, and the button remains clickable without the mouse recapturing. Keyboard/mouse feel and rendered camera transitions still require hands-on review.

## Original Phase 1 demo

`Assets/Scenes/PhaseOne.unity` remains available for the original single-planet movement demo.

`PlanetGravity` supplies constant radial acceleration about its transform. `SphericalPlayer` applies gravity in physics steps, aligns a Rigidbody capsule to local up, accelerates along the tangent plane, and probes the assigned planet for grounded jumping. Diagonal input is normalized and airborne steering is reduced. `PlanetCamera` transports its heading with local up, smooths its following position, limits pitch, and prevents the camera from crossing the planet surface.

Assign the starting planet and movement camera in the player Inspector; populate `gravitySources` for multiple planets. Each source uses a centered SphereCollider with uniform scale; the player uses a unit-scale Y-axis capsule. Tune gravity acceleration, influence height, edge falloff, walk/run speeds, three jump heights and the consecutive landing window, air control, gravity turn speed, oxygen capacity, camera distance, and smoothing in the Inspector. Planets are static in this demo. Empty source lists retain single-planet behavior.

Use **GravityGame > Create Phase 1 Demo** to recreate the demo scene. This prompts to save open scene changes. The original SampleScene and build scene list are preserved; add PhaseOne to a build profile when building the demo.

Manual checks: walk a complete circuit through both poles and the underside; release movement to stop; compare diagonal and straight speed; jump, land, and hold Space to confirm no automatic repeated jump; orbit near the horizon; release and recapture the pointer. Confirm the camera stays outside the planet and the Console has no errors.

Automated validation: with the project closed in the editor, run Unity with `-batchmode -nographics -projectPath <project> -executeMethod GravityGame.Editor.PhaseOneDemo.Validate -quit -logFile <log>`. It recreates PhaseOne, checks scene references and gravity at all six cardinal directions, tests surface probes and the center fallback, and simulates six player drops to confirm grounding. Look for `PHASE_ONE_VALIDATION_PASSED`. Run this on a temporary copy if the project is already open. These checks do not replace the manual input and camera checks above.
